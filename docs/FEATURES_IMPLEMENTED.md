# Реализованные функции RedChat

## Профиль и файлы

- Аватар пользователя: `POST /api/auth/avatar`, multipart-поле `avatar`, до 5 МБ, JPG/PNG/WEBP/GIF.
- Вложение к сообщению: `POST /api/conversations/:conversationId/files`, multipart-поле `file`, до 15 МБ.
- Файлы вложений скачиваются по `GET /api/files/:id`. Endpoint требует сессию и проверяет, что пользователь входит в диалог.
- Аватары хранятся в `uploads/avatars`, вложения — в `uploads/files`. В Docker обе папки находятся в volume `uploads_data`.

## Личные диалоги

- `GET /api/users?q=...` — поиск пользователей.
- `GET /api/conversations` — общий чат и личные диалоги текущего пользователя.
- `POST /api/conversations/direct` с `{ "user_id": "..." }` — создать или получить существующий диалог один-на-один.
- Участники личного диалога сохраняются в `conversation_members`. API истории и отправки проверяет членство.

## Сообщения

- `GET /api/conversations/:conversationId/messages?limit=30&before_id=...` — cursor pagination.
- `POST /api/conversations/:conversationId/messages` — HTTP-отправка сообщения.
- WebSocket `/ws` принимает событие `{ "type": "message", "conversation_id": "...", "content": "..." }`.
- `PUT /api/messages/:id` — изменить текст собственного сообщения.
- `DELETE /api/messages/:id` — удалить собственное сообщение и его файлы.
- `POST /api/messages/:id/reactions` с `{ "emoji": "👍" }` — переключить реакцию. Поддерживаются 👍 ❤️ 😂 😮 😢 🔥.

## Redis Pub/Sub

Backend публикует события в канал `redchat:chat:events`. Каждый backend экземпляр слушает этот канал. В envelope передаются ID получателей и JSON payload; экземпляр отправляет payload только локальным WebSocket-соединениям этих пользователей. Для общего чата получатели — все пользователи, для личного диалога — только его участники.

Redis Pub/Sub не заменяет PostgreSQL: PostgreSQL остаётся источником истины для сообщений, диалогов, вложений и реакций.

## Origin allowlist

`ALLOWED_ORIGINS` — comma-separated список точных origin, например:

```env
FRONTEND_ORIGIN=http://localhost
ALLOWED_ORIGINS=http://localhost
```

Для другого домена укажите его точный origin с протоколом и, если нужно, портом. Wildcard не используется. Отсутствующий `Origin` также отклоняется.

## Проверка сценариев

1. Поднимите проект через `docker compose up --build` и создайте два аккаунта в разных браузерах.
2. С первого аккаунта откройте поиск пользователей, найдите второй аккаунт и создайте личный диалог.
3. Отправьте текст в личном диалоге и убедитесь, что он доступен только двум участникам.
4. Загрузите аватар и прикрепите файл; скачивание файла должно требовать авторизации и участия в диалоге.
5. Проверьте редактирование/удаление своего сообщения и переключение реакций.
6. Создайте более 30 сообщений и нажмите «Загрузить предыдущие сообщения».
7. Запустите второй backend экземпляр на той же PostgreSQL и Redis, подключите пользователей к разным экземплярам и проверьте доставку событий через Redis Pub/Sub.
8. Проверьте подключение WebSocket с origin, отсутствующим в `ALLOWED_ORIGINS`: сервер должен вернуть 403.

Миграции из `back/internal/store/migrations` автоматически выполняются при старте backend. Не удаляйте Docker volumes при обновлении схемы, если нужно сохранить пользовательские данные.
